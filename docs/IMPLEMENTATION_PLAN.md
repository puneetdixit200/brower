## Execution rules and gates

1. At each batch start, capture `git status --short`, read all touched code and current matrix rows, and reserve exclusive file ownership. Existing edits are valuable; do not reset, overwrite, or commit them implicitly. A worker handles one bounded task or a tightly coupled pair. Separate worktrees are preferred when overlap is likely; this checkout's uncommitted changes do not copy automatically to them.
2. Luna medium workers implement code, focused tests and short evidence reports. Use Luna medium for independent review and difficult integration as well. Keep handoffs bounded, avoid duplicate investigation, and independently inspect evidence rather than accepting implementation assertions as proof.
3. Every task exits with focused tests, typecheck/lint where relevant, and a disposable-profile headed test when behavior crosses UI, extension, server, or Chromium boundaries. Use only local fixtures and dummy provider credentials for routine checks. Preserve raw benchmark data and screenshots where relevant. A failed or impossible live test leaves the row PARTIAL or BLOCKED with the exact missing evidence.
4. Integration gate after each batch: inspect the combined diff, run `git diff --check`, affected package checks, and the relevant headed smoke. Reconcile `FEATURE_MATRIX.md`, `PROGRESS.md`, and limitations with exact evidence. Do not turn an upstream baseline, mock response, source inspection, or unit test alone into packaged Aster PASS.
5. Development and package gates are distinct. Source, fixture, and WXT development-extension work may proceed before a runnable native Aster package exists; record this as provisional evidence. Any task requiring browser chrome, incognito, OS integration, or packaged service behavior stays PARTIAL/BLOCKED until retested in the Aster package. T20a is the early native-build-host/bootstrap dependency; T20b is the later release package and install gate. Earlier work compiled native objects, but a complete linked Aster browser build and runnable package have not been verified. A monitored low-concurrency full-build trial with `BROWSEROS_NINJA_JOBS=2` remains to be assessed against current host resources and source/resource integration. Reassess actual memory and swap pressure before starting, and never weaken the sandbox.
6. Release gate: Aster-owned binary and update identity, sandbox and profile isolation, privacy/permissions review, licensing, Omarchy install/uninstall, matched performance, and fresh-profile browser regression must all pass.
