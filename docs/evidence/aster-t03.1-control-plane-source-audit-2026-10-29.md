# T03.1 control-plane source inventory

**Date:** 2026-10-29
**Scope:** Read-only source audit of the BrowserOS agent HTTP control plane, BrowserOS neo (`claw-server`) HTTP/MCP control plane, OAuth callback listener, and repository-visible launch inputs for CDP/proxy listeners.
**Result:** Source inventory only. This is not security acceptance, a packaged-runtime audit, or proof of the listeners observed on an installed build. Keep **S03 PARTIAL**.

## Summary

The legacy TypeScript sidecar starts its HTTP server on `127.0.0.1` and its CDP backend connects to the configured browser CDP port. The newer Rust `claw-server` separately binds its HTTP API to `127.0.0.1`; its `/mcp` streamable HTTP service has browser-request hygiene but no bearer check in the inspected route/middleware source. The TS `/mcp` endpoint does require either a server-issued browser-tool lease or the persistent MCP bearer token for POST requests; lease callers can receive the conversation-scoped writable capability while bearer callers are read-only. Both architectures publish/use a browser-proxy port, but the repository evidence inspected here only shows launch arguments/configuration and the servers' advertised URL; it does not prove the Chromium proxy listener's actual bind, authorization forwarding, or packaged behavior. **Aster product source selects the legacy TypeScript `aster_server` as its intended Linux development sidecar and does not select the separate neo `claw-server`** ([`aster-descriptor.ts:6-23`](../../packages/browseros-agent/scripts/build/server/aster-descriptor.ts#L6), [`product.py:52-76`](../../packages/browseros/bos_build/products/aster/product.py#L52)). This is source intent only: native integration is still patch text and no linked development or release package proves the actual process set. Treat neo-specific rows below as comparative unless package evidence shows otherwise.

The TS sidecar's lazy OAuth callback listener binds `127.0.0.1:1455`. Its `/cancel` handler is unauthenticated and can stop that local callback listener. Successful code exchanges require an in-memory pending `state` checked by the token manager; an OAuth `error` callback is rendered before code/state validation. The main TypeScript server's shutdown endpoint accepts an originless local-loopback request by design; loopback peer/Host checks are not authentication against other local processes.

Aster process-selection source: [`aster-descriptor.ts:6-23`](../../packages/browseros-agent/scripts/build/server/aster-descriptor.ts#L6) builds `apps/server/src/compiled-bootstrap.ts` as `aster_server`; the Chromium patch [`browseros_server_config.cc:60-75,89-97`](../../packages/browseros/chromium_patches/chrome/browser/browseros/server/browseros_server_config.cc#L60) declares the Aster descriptor and returns it for `IsAsterProduct()`, behind `ASTER_UNPACKED_DEV_EXTENSION`. The patch is source intent, not evidence that the adjacent native checkout has applied it or that a linked binary stages/starts the server.

## Route and authority observations

- The legacy TS global CORS allowlist and `requireTrustedOrigin` constrain a present Origin, but neither requires Origin nor proves the request peer is local for every route. The actual server bind is loopback, and the stricter helper is only mounted on the route families listed above.
- The legacy `/mcp-manager/access` route returns the persistent token, so correctness depends on the parent `/mcp-manager/*` trusted-app middleware plus the specific required-Origin guard; this must be exercised from the signed extension and hostile browser origins in the packaged proxy path.
- Legacy MCP POST authentication and scope differ: bearer-only is read-only; a valid lease may carry write authority. The source-only review did not test lease lifecycle against real extension/agent traffic.
- Neo API and MCP depend on loopback binding as the primary boundary. Neo's broad `Access-Control-Allow-Origin: *` is not authorization. The request middleware's narrow origin checks on recording ingest and update-ready must not be generalized to other routes. These neo observations are not evidence of Aster exposure because its current product descriptor selects the TypeScript sidecar instead.
- Neither localhost binding nor `Host: localhost` authentication isolates the service from other local processes. This is especially material for the TS OAuth callback `/cancel` endpoint and for neo's unauthenticated `/mcp` only if that separate server is actually packaged. The TS `GET /mcp` is an unauthenticated status/discovery response; MCP protocol POST requests require bearer or lease authorization. The callback handler branches by URL path but does not inspect the HTTP method, so both callback paths are method-agnostic in this source; error callbacks render before code/state checks.
- The server source does not own the CDP or Chromium proxy listeners. Runtime socket observations and Authorization forwarding cannot be established from a server-side route unit test.

## Evidence still required before S03 can pass

1. Inspect authoritative native Chromium proxy implementation and packaged startup code; establish the listener's actual address, endpoint mappings, request-header forwarding/preservation, and authorization behavior.
2. On an installed release build, enumerate server, callback, CDP, and proxy sockets. Confirm IPv4/IPv6 behavior and that no supposedly local listener is reachable over a non-loopback interface.
3. Use an independent external MCP client through the packaged endpoint. Prove missing/incorrect bearer denial, valid bearer read-only behavior, valid conversation lease behavior, and which layer rejects unauthorized mutation.
4. Exercise every route family with allowed extension Origin, hostile Origin, absent Origin, forged Host, and a non-loopback peer where deployment permits; specifically test state-read exceptions, token handoff, shutdown compatibility, OAuth callback state, and no-auth neo APIs.
5. Verify hosted-mode `/v1` is fronted by the intended authenticated deployment boundary; source only shows conditional route mounting and no route-local auth layer.
6. Record exact BrowserOS/neo/native package versions, launch arguments, effective listener table, and request results as release evidence.
7. Build and inspect the Aster native development binary to prove the source-selected `AsterServer` resources are staged and launched; then scope runtime control-plane checks to the observed process set. Source currently selects the legacy TypeScript `aster_server`, but a compiled package has not proved this.
