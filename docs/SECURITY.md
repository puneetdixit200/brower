# Security baseline

- Preserve Chromium sandbox and native permission/profile boundaries.
- Do not send passwords, cookies, passkeys, session tokens, API keys, or profile databases to an LLM.
- Bind any local CDP/MCP/control interface to loopback and authenticate it.
- Browser page content is untrusted input; authorization must be enforced by tools, not prompt text alone. Deny takes precedence over ask/allow.
- Require explicit approvals for external sends, posts, purchases, destructive changes, and sensitive file writes.
- No credentials, real user tasks, or existing browser profiles in tests.
- Model calls, analytics, sync, and update traffic must be disclosed and user controlled.
- S04: app and agent optional diagnostics default off behind private persisted consent and revision-bound transports. Sentry event envelopes retain bounded technical metadata; server counters use a fixed field allowlist, and app metrics do not forward conversational data to native logMetric. Development runtime tests cover failed revoke, cross-tab state, offline retry, ON/OFF restart persistence, private state permissions and origin denial. Consent is not anonymity; native Aster package, remote processing/retention and broad provider/log-sink verification remain open.
- S05 is PARTIAL / BLOCKED. WXT uses a stable Aster-specific development public key (ID `oifdmombnijnaiocijiacjhajbnpdlhb`) without an updater URL; `externally_connectable.ids` is explicitly empty by default to deny extension callers, while `web_accessible_resources` is absent. Fresh headed development runs verified default external denial and configured reporter access with a fresh diagnostics response; release packaging remains unverified. Explicit release key and updater values must be paired. Public keys are parsed as DER SPKI and rejected if they derive to a BrowserOS extension ID. Product-site and update URLs are checked for HTTPS and disallowed hosts, but these checks do not establish domain ownership. The current emitted development manifest was inspected. Release key custody, update service, verified domain ownership, release-origin configuration, and reporter deployment ownership remain release prerequisites.
- Preserve AGPL-3.0-or-later and third-party license notices.

## Verified Aster controls

- The supervised Linux dev server and CDP listeners were observed on loopback only. This is dev-run evidence, not proof about a future packaged browser.
- `/klavis/*` routes require a trusted local extension request. Route tests reject originless activation and accept the trusted extension origin.
- `/mcp-manager/*` connector install/uninstall routes require a trusted extension request. `/oauth/*` requires an explicit trusted app origin for every method, including the state-starting GET route. Guards are registered before the Hono route mounts; tests cover blocked originless mutations and successful extension-origin requests.
- `/chat/*` now requires an explicit trusted extension origin for every method. This covers chat submission, conversation state/stream reads, panel assignment, stop, and session deletion; originless local callers cannot submit browser work or inspect/stop a run. Chat route tests verify trusted UI traffic continues to work.
- Internal agent MCP calls require a server-issued conversation lease. External `/mcp` requests require the persisted bearer token unless they carry a valid server-issued internal lease. The live BrowserOS endpoint and SDK client path were verified; packaged proxy forwarding and a separately installed client remain unverified.
- The server no longer starts its Klavis connector proxy during ordinary startup. The home and chat surfaces defer remote integration queries until the user opens Connect Apps; visiting the dedicated Apps settings page also activates it.
- In a network-isolated headed run, startup and the closed home made no Klavis requests during the initial observation window. Opening Connect Apps triggered the integration fetch and connector attempt, both blocked by the isolated namespace. This confirms the opt-in boundary without establishing successful cloud behavior.
- Focused auth tests passed. The complete CDP/MCP route set, packaged production ports, telemetry, updater, and all other outbound requests still need review. Both `/system/shutdown` and `/shutdown` require a loopback peer and a `localhost` or `127.0.0.1` Host; any supplied Origin must be explicitly trusted. Originless loopback requests remain supported for shipped BrowserOS C++ restarts. This is not an authentication boundary against another local process, which can make an originless loopback request and shut down the server.
- The agent checks proposed tool names and descriptions before execution. It requests approval for browser `act`, code execution, file transfers and mutations, browser organization/window changes, external connector names/descriptions that indicate side effects, and any tool outside the explicit read-only allowlist. A headed isolated denial run confirmed `act.click` did not execute after Deny. Tool semantics are not statically verified; a tool with misleading metadata could still be misclassified. Guard/Full modes and user-editable allow/ask/deny rules are not implemented.
- Approval responses require a trusted extension origin and must match an unresolved request in server-held conversation history. Unknown, stale, or duplicate IDs fail closed. HMAC approval signatures use a process-scoped secret, so unresolved approvals cannot be resumed after server restart. Headed isolated runs verified both Deny and Approve; the approved `act.click` changed a harmless local fixture button after an explicit snapshot. External send/payment approvals and restart recovery remain untested.


## External MCP access

- External `/mcp` POST requests require `Authorization: Bearer <token>` unless the request carries a valid server-issued internal lease. The token is random, persistent across restarts, stored under the BrowserOS state directory with owner-only permissions, and compared in constant time.
- `/mcp-manager/access` returns the token only to a JSON POST with an explicit trusted extension origin. A headed, network-isolated BrowserOS run verified that the settings page receives the token and that the configured external-facing `/mcp` endpoint denies requests without the bearer header and accepts it when present. One-click integrations install the header, and startup reconciliation restores it while preserving the existing URL when needed.
- An SDK client completes authenticated initialization and tool listing in a wire-level test; separately installed end-user clients and packaged production builds are still release checks. Packaged builds must ensure that the state directory is private and that the proxy forwards Authorization unchanged.

## Local memory

- User-entered notes are stored in the local SQLite database and mirrored to a generated Markdown file. Retrieval defaults off and is opt-in. Common credential assignment patterns and credential-bearing source URLs are rejected; this filter is not a complete secret detector.
- A headed, network-isolated BrowserOS run verified opt-in default, add/search/edit/delete through the extension UI and authenticated local API; the test note was deleted and the dev profile was disposable.
- No automatic chat or browsing-history extraction is active. A user can explicitly attach up to three saved notes or up to three selected browser-history entries to a home-composer request; these go to that request's selected provider and may be retained under the conversation's existing history setting. The history picker strips URL paths and query strings, persists no history copy, and is disabled in incognito contexts. Memory settings and the memory picker also check the hosting browser window and fail closed while that check is pending; memory API calls marked as incognito are rejected. A headed off-the-record attempt in BrowserOS v0.51.0 was blocked by Chromium before extension APIs loaded, so runtime persistence behavior remains unverified. The request marker is a built-in extension behavior control, not a boundary against a hostile local process that can spoof an extension origin.
- Normal-window side-panel drafts are stored in extension local storage under their owning tab ID. Draft reads and writes are skipped for an incognito or unresolved owning window. OTR runtime verification remains unavailable in the tested BrowserOS build because Chromium blocked the unpacked extension page.
